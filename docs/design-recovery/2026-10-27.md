## Repository-specific records

### D15 — MÄG-RISO: the browser as a working print studio

**Use when:** When extending magical-risograph, print/halftone effects, physics desks, ink separation, movable type, or tactile editorial interfaces.

[Recovered intent] MÄG-RISO imagines eight stations: physics desk, halftone lab, stencil archive, drum isolator, print queue, ink library, composing room, and project specimen. The product is a material workflow—arranging, separating, setting type, registering, pulling a proof—not a riso-colored landing page.

[Stack and material] The documented approach is vanilla HTML/JS through Vite, with Matter.js, GSAP, Canvas 2D, SVG filters, procedural Web Audio, and hash navigation. Preserve ink pressure, paper stock, registration offsets, overprint, letterpress sequence, and proof export as distinct controllable mechanisms.

[Observed boundary] The README contains capability claims about offline/PWA behavior, queue progress, form jobs, physical simulation, and type wear; this pass inspected the README/tree, not each runtime behavior. The single-file architecture is a current structural choice, not a requirement that future modules remain tangled.

[Repair resolution — proposed] Extract print recipes, station state, rendering, and input/audio adapters behind narrow interfaces while preserving the working single-file distribution if useful. Mark simulated queue advancement clearly. Compare the exported proof with the visible composite. Keep physical-copy claims distinct from screen appearance.

[Reimagined horizon] A playable studio and reusable print-effects toolkit: workshops, portfolio storytelling, type/ink experiments, and exportable authored assets. Physical placement, source licensing, and genuine print color management remain explicit future integrations.

[Carry-forward test] One image passes through separation, registration, stock/pressure controls, proof rendering, save/reload, and export. Every station remains reachable by keyboard and touch; sound and desk physics are optional.

## Practical continuation contract

1. Re-read current repository instructions and source before implementation. The baseline above identifies this publication, not a permanent execution HEAD.
2. Retain the full design horizon separately from the current demonstrator. Name what the demonstrator preserves, approximates, defers, or cannot prove.
3. Map tokens and controls to actual consumers with explicit units, ownership, accessible alternatives, and observable effect.
4. Complete the relevant interaction/error/cancellation states before promoting a reusable component.
5. Pair source/runtime checks with human correspondence review against the actual visual inspiration.
6. Keep proposed repairs unexecuted until a later implementation records its own revision, checks, and evidence.
